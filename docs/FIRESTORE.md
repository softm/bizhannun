# 계정별 Firestore 저장

사업자한눈은 Firebase Authentication의 `uid`를 기준으로 거래처·태그·메모·내 사업 프로필·상태 조회 이력·변경 기록·일괄 확인 기록을 저장합니다. 로그인만 유지하는 구성이 아닙니다. 다른 기기에서 같은 로그인 방식과 계정을 사용하면 해당 계정의 저장 내용을 불러옵니다.

## 데이터베이스 설정

연결 대상은 사업자한눈 전용 Firebase 프로젝트 `biz-hannun`의 Firestore **Enterprise Native**, 데이터베이스 이름 `bizhannun`, 서울 `asia-northeast3`입니다. 인스턴스가 생성되어 있고 실시간 업데이트를 사용합니다. 서버가 내려 주는 `/api/config`의 `firestore.databaseId`로 이름을 지정하며, 설정값을 바꾸면 다른 인스턴스를 선택할 수 있습니다.

여러 기기에서 저장한 변경을 바로 알리는 기능이 필요하므로 Enterprise에서도 표준 SDK의 문서 조회·트랜잭션·`onSnapshot`을 사용합니다. 분석용 Pipeline 쿼리를 수행하는 앱은 아닙니다. 공개 지원사업 목록은 기존 정적 JSON을 사용하며 개인 계정 문서와 섞지 않습니다.

| 저장 항목 | 저장·접근 방식 |
| --- | --- |
| 거래처, 태그, 메모, 거래처별 조회 이력 | 로그인한 uid의 독립 기록으로 저장 |
| 내 사업 프로필 | 같은 uid에서 조회·수정 |
| 변경 기록·확인 표시·일괄 조회 결과 요약 | 같은 uid에서 조회·수정 |
| 브라우저의 API 서버 주소 | 이 기기의 설정으로 유지. 클라우드로 복사하지 않음 |
| 비로그인 상태에서 만든 기존 정보 | 기기에 유지. 사용자가 ‘계정으로 가져오기’를 선택해야 업로드 |
| 인증키·SNS access token | 이 저장소에 저장하지 않음 |

## 저장 구조

```text
users/{uid}/bizhannunWorkspace/main
users/{uid}/bizhannunManifests/{generation}-{part}
users/{uid}/bizhannunObjects/{recordVersion}-{part}
```

`main` 문서에는 현재 revision, manifest 위치와 해시, 항목 수, 서버 갱신 시각을 둡니다. 각 거래처·프로필·이벤트·조회 요약은 독립된 불변 기록으로 저장합니다. 각 기록의 JSON이 크면 최대 180,000 UTF-8 바이트의 조각으로 나눕니다. 본문 인덱스는 사용하지 않습니다.

새 저장은 다음 순서로 진행합니다.

1. 기존 입력 검증기로 전체 정보를 검증합니다. 클라우드에서도 동일한 사업자번호, 상태 값, 이력, 날짜 검증을 적용합니다.
2. 직전에 불러온 revision과 서버의 현재 revision이 일치하는지 확인합니다.
3. 변경된 기록만 새 식별자로 업로드합니다. 변경되지 않은 기록은 기존 참조를 유지합니다.
4. 전체 기록의 참조를 담은 새 manifest를 업로드합니다.
5. Firestore 트랜잭션에서 revision을 다시 비교하고 `main`을 한 번에 교체합니다.
6. 서버에서 갱신 시각과 최종 포인터를 다시 읽은 후에만 저장 완료로 표시합니다.

1,000개 CSV 가져오기는 여러 배치로 나누되 마지막 포인터 교체 전에는 새 목록을 공개하지 않습니다. 실패한 부분 업로드가 기존 목록을 덮어쓰지 않습니다. 다른 기기의 변경이 먼저 저장되면 현재 입력은 충돌 오류로 남기고 최신 정보를 불러오도록 안내합니다. 자동으로 한쪽의 변경을 버리거나 합치지 않습니다.

클라우드 계정 데이터는 브라우저 공용 IndexedDB에 별도 복사하지 않습니다. SDK의 기본 메모리 캐시를 사용하고, 로그아웃 또는 계정 변경 시 화면 상태와 구독을 정리합니다. 오프라인 저장을 성공으로 표시하거나 나중에 자동으로 올리는 작업 대기열은 제공하지 않습니다. 응답을 받지 못한 저장은 최신 데이터를 다시 불러와 성공 여부를 확인합니다.

최대 항목 수는 기존 앱과 같습니다. 거래처 1,000곳, 거래처별 이력 50개, 변경 기록 1,000개, 일괄 확인 요약 100개입니다. 클라우드 전체 기록의 직렬화 크기는 64MiB로 제한하며 초과 시 저장 전체를 거절합니다. 큰 기록을 저장하기 위해 내용을 추가로 잘라 저장하지 않습니다. 입력 필드 길이는 기존 앱의 검증·정규화 규칙을 따릅니다.

## 기존 브라우저 정보 가져오기

가져오기 전 신규·중복 거래처 수를 미리 확인합니다. 같은 사업자번호가 이미 클라우드에 있으면 클라우드 거래처와 메모를 유지합니다. 신규 거래처의 확인 이력도 함께 가져오며 식별자가 충돌하면 새 식별자를 부여하고 변경 기록의 참조를 함께 수정합니다. 내 사업 프로필은 클라우드 프로필이 비어 있을 때만 가져옵니다. 기기 원본은 자동 삭제하지 않으므로 필요하면 먼저 JSON 백업을 받을 수 있습니다.

## 보안 규칙과 검증

`firestore.rules`는 초기 규칙입니다. 경로의 uid와 `request.auth.uid`가 같아야 읽고 쓸 수 있습니다. 공개 사용자 목록, 다른 계정 문서 조회, 임의 권한 필드, 광범위한 하위 경로 쓰기를 허용하지 않습니다. 문서의 허용 필드, 타입, 크기, 식별자, 생성 시각과 revision 증가를 검사합니다. 본문 조각은 만들고 삭제할 수 있으며 기존 조각을 수정할 수 없습니다.

조각 본문은 직렬화된 업무 데이터이므로 Firestore Rules가 JSON 내부 필드까지 해석하지는 않습니다. 소유자 격리는 Rules에서, 내부 스키마·원본 해시·사업자 일치 검증은 앱에서 수행합니다. 본문 안의 값으로 권한을 결정하지 않습니다. 규칙 검증은 구현에서 확인한 공격·오류 범위를 입증하며 모든 위협의 부재를 보증하지 않습니다.

| 검증 | 기대 결과 |
| --- | --- |
| 소유자의 거래처 저장·수정·다른 클라이언트 재조회·삭제 | 성공 |
| 미로그인 및 다른 uid의 읽기·목록·쓰기·삭제 | 거절 |
| 다른 uid로 소유권 변경, 사용자 목록 또는 collection-group 조회 | 거절 |
| 임의 `isAdmin` 필드, 필수 필드 누락, 잘못된 타입·크기·날짜 | 거절 |
| 불변 기록 수정, revision 초기화·건너뛰기·이전 상태 재저장 | 거절 |
| 1MiB를 넘는 거래처 이력, 1,000개 거래처 저장 | 조각 저장 후 무손실 복원 |
| 중간 업로드 실패, 계정 변경, 무결성 오류 | 기존 포인터 유지 또는 로드 거절 |
| 완료 응답 유실 뒤 늦게 성공한 트랜잭션 | 조각을 유지하여 재조회 가능 |

Java 21 이상과 Node.js 22 이상에서 실행합니다.

```bash
npm ci
npx -y firebase-tools@15.34.0 emulators:exec --only firestore --project demo-bizhannun "node --test tests/firestore-rules.test.mjs"
node tests/cloud-storage.test.mjs
```

일반 `npm test`에서는 에뮬레이터가 연결되지 않았으면 Rules 시험을 건너뜁니다. 에뮬레이터 시험을 별도로 실행해야 Rules 문법과 실제 허용·거절을 검증할 수 있습니다. `firebase.json`에 운영 DB와 같은 Enterprise 에뮬레이터 모드를 명시했습니다. 운영 프로젝트의 실제 계정 데이터로 시험하지 않습니다.

2026-10-20 검증 결과: 저장 어댑터 시험 13개가 통과했습니다. Firebase CLI 15.34.0과 공식 Firestore Emulator 1.22.0의 **Enterprise 모드**에서 공개된 운영 Rules와 같은 규칙으로 실제 SDK 저장·수정·재조회 및 접근 거절 시험 7개도 모두 통과했습니다. 복구된 소스에 대해 다시 실행한 결과이며 가상 계정과 합성 데이터만 사용했습니다.

## 배포

`firebase.json`은 이름이 `bizhannun`인 데이터베이스의 규칙과 인덱스를 가리킵니다. 프로젝트 ID를 확인한 뒤 명시적으로 지정합니다.

```bash
npx -y firebase-tools@15.34.0 deploy --only firestore:rules,firestore:indexes --project biz-hannun
```

프로젝트 ID를 생략해 다른 앱의 활성 프로젝트에 배포하지 마세요. 신규 운영 인스턴스에 규칙을 배포하기 전에는 로그인에 성공해도 저장 요청이 거절될 수 있습니다.

## 오래된 조각 정리

정상 저장이 완료되면 이전 manifest와 더 이상 참조되지 않는 이전 기록 조각을 정리합니다. 새로 만든 식별자를 재사용하지 않고 현재 목록에서 참조하는 기록은 삭제 대상에서 제외합니다. 경쟁 저장이 revision 충돌로 거절되면 그 요청이 새로 만든 조각만 정리합니다. 다른 기기가 오래된 manifest를 읽는 도중 정리된 경우에는 새 포인터를 확인한 후 다시 읽습니다.

브라우저 강제 종료·네트워크 단절·저장 완료 응답 유실 시에는 미사용 조각이 남을 수 있습니다. 완료 여부가 불확실한 조각을 즉시 삭제하면 실제로 저장된 기록을 손상할 수 있어 자동 삭제하지 않습니다. 운영자는 주기적으로 다음 기준으로 관리해야 합니다.

1. 현재 `main`과 manifest를 읽고 활성 기록 조각의 전체 참조를 계산합니다.
2. 7일 이상 지난 미참조 manifest·기록만 후보로 수집합니다. 생성 시각이 최근인 조각은 업로드 진행 중일 수 있어 제외합니다.
3. 삭제 직전에 같은 uid의 현재 revision과 generation이 바뀌지 않았는지 다시 확인합니다. 바뀌었으면 중단하고 새 참조 목록으로 재계산합니다.
4. 처음에는 후보 수와 크기만 확인하고 백업 후 제한된 배치로 삭제합니다. 활성 참조 또는 판독 실패한 계정의 조각을 삭제하지 않습니다.

자동 정기 관리 작업은 이 버전에 포함되지 않습니다. 다수 사용자를 받기 전 사용량 모니터링과 위 정리 절차를 운영 작업에 포함해야 합니다.
